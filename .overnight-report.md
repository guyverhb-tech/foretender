# Overnight report — integrate gate tolerant of integrator artifact name

Run: 2026-08-13, branch `claude/overnight-20260813-105426-fix-integrator-artifact-name`
Task: make the harness integrate gate accept `.harness/integration-report.md` as
well as the canonical `.harness/integration-log.md`.

## What changed

One file: `.claude/hooks/lib/harness.sh`. Added an `integrator)` branch at the
top of `harness_artifact_reason` that accepts **either**
`.harness/integration-log.md` or `.harness/integration-report.md` when the file
exists and is >= 120 bytes (the same size floor the generic path applies — the
integrator owes no VERDICT block, so existence + size is the whole check). The
failure message still names `integration-log.md` as the file to write, so the
canonical name is unchanged. `f` was added to the function's `local` list for
the loop variable.

Because both `.claude/bin/advance-phase.sh` (orchestrator path) and
`.claude/hooks/artifact-gate.sh` (SubagentStop hook) call this shared function,
one edit fixes both callers; neither caller was touched, per the task spec.
`harness_artifact_path` still returns the canonical `integration-log.md` (it
feeds `harness_next_phase`'s verdict lookup, which the integrator branch
ignores — `integrator) printf 'done'` is unconditional — so no change needed
there). Nothing in the agent definition or SKILL.md was renamed.

## Uncertainties

- A file that exists but is under 120 bytes now gets the combined
  "without writing … or wrote it essentially empty" message instead of the
  generic path's distinct "essentially empty" wording. The task said "present
  and non-empty is enough"; I kept the existing 120-byte floor (matching the
  generic check and the smoke-test spec's ">=120 bytes") rather than accepting
  any non-zero file, so a two-byte stub still can't pass the gate.
- The global templates at `~/.claude/skills/scaffold-harness` still carry the
  old single-name check — upstreaming is a separate manual step, per the task's
